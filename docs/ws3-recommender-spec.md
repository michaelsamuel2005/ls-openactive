**Owner of the build: Clarence** (WS3 lead) · **Evaluation design: Fahmi** (design BEFORE build) · **This spec + input artefacts: Michael** (WS2 interface) · Status: kickoff, 4 July 2026.
Governing decisions: D-010/D-011 (layer separation), D-015 (pivot to LO4), proposal §7 WS3 & §8. Rules: `docs/engineering-rules.md`. **This is the project's LO4 centrepiece and its largest unbuilt marks block.**

---

## 1. What it is (and is not)

A **deterministic, transparent discovery engine**: hard-constraint filtering → content-based similarity to a user profile → **equity-aware re-ranking** with `score = α·relevance + (1−α)·equity`, α swept, never fixed silently.

**It is NOT:** a learned model; a system with accuracy claims (there is no interaction ground truth — this is a hard, logged constraint, not a modesty flourish); a booking system. Never evaluate against synthetic labels as if they were accuracy. The honest evaluation IS the contribution (§5).

**Deliberately refused upgrades (record them — the refusals are part of the method):** collaborative filtering / learned embeddings (unsupportable without interaction data); **optimising α or declaring a "best α"** (a category error — with no ground-truth objective, α is a policy dial for London Sport, and the deliverable is the characterised trade-off, not a recommended setting); a live user study (out of scope; the proposal's heuristic-walkthrough path stands); production/API engineering beyond the proof-of-concept. Each refusal is defensible from the data's limits and belongs in the report's methods discussion.

## 3. Functional specification (Clarence)

**3.1 Hard filters (applied first, deterministic, all optional per query):**
- `max_price` (float; free-only = 0) — on `price`.
- `max_distance_km` (float) from a user point (lat/lon) — per the engineering rules, reproject both points to EPSG:27700 and use Euclidean distance (metre-true at London scale; `pyproj`/`geopandas` already available). Haversine on WGS84 is a numerically equivalent alternative at this scale but the projected route keeps one convention across the project — if used instead, document why. Never arithmetic on raw degrees. Alternatively `borough` equality (no geometry needed).
- `activity_types` (list) — match on `activity_type`.
- `require_access_info` (bool) — on `has_access_info`, with the absence-≠-inaccessible caveat surfaced in output.

**3.2 Relevance (content-based similarity):** user profile = preferred activity types + price band + home point. Feature space: one-hot activity type ⊕ scaled price ⊕ (optionally) geographic proximity decay. Cosine similarity; scikit-learn permitted (already a dependency). Fully deterministic — any tie-break by stable sort on `id`.

**3.3 Equity term (this is where WS2 plugs in):**
`equity_i = w_a·affordable_i + w_c·access_info_i + w_u·underserved_i`, where `affordable = is_free or price ≤ threshold`, `access_info = has_access_info`, and **`underserved` = the session's borough's `gap_index_z` min-max scaled to [0,1] over the 32 scored boroughs** (alternative: binary `is_priority_borough` — implement both, report both). Weights equal by default; document any change in the decision log.

**3.4 Ranking:** `score = α·relevance + (1−α)·equity`, both components min-max scaled to [0,1] first. **Scaling scope (fixed here so behaviour is well-defined):** `equity` is query-independent → scaled ONCE over the full 494-row catalogue; `relevance` is query-dependent → scaled per query over the post-filter candidate set (if all candidates tie, define relevance ≡ 0.5 and note it in the trace). **Tie-breaking:** primary by score; at the sweep endpoints break ties lexicographically by the zero-weighted component (at α=1: relevance, then equity, then `id`; at α=0: equity, then relevance, then `id`) — this preserves Pareto-optimality at the endpoints (see P1); `id` remains the final, total-order tie-break everywhere. **α ∈ {0, 0.25, 0.5, 0.75, 1.0}** reported everywhere — the α-sweep IS the headline exhibit (the relevance–equity trade-off made visible).

**3.5 Output:** top-k (default k=10) with a per-item trace: which filters passed, relevance, equity components, final score, borough + quadrant. Transparency is a feature — the report will show a worked example.

## 4. Personas (transparent, illustrative — never "users")
6–10 documented synthetic personas spanning the constraint space (e.g., low-income parent in a priority borough, free-only; wheelchair user needing access info; older adult, low-intensity preferences, outer borough; time-poor shift worker — noting the time-filter gap). Personas stress-test behaviour and illustrate the α trade-off. They are labelled illustrative in every output. Final set agreed by Clarence + Fahmi, committed as `docs/ws3-personas.md`.

## 5. Evaluation contract (Fahmi — design finalised BEFORE the build fixes behaviour)

Beyond-accuracy metrics ONLY, each reported per α value, per persona and averaged:
- **Catalogue coverage@k** — share of the 494 series ever surfaced across the persona set.
- **Intra-list diversity@k** — 1 − mean pairwise similarity of the recommended list.
- **Affordable share@k** — free or ≤ threshold.
- **Access-info share@k.**
- **Priority-borough share@k** and **geographic spread@k** (distinct boroughs; optionally a concentration index).
- **Relevance cost** — mean relevance of the list vs the α=1 list (the price paid for equity, stated plainly).

Every metric is reported as a **distribution over the persona set** (median + IQR or min–max), not a bare mean, with a bootstrap-over-personas interval for the headline metrics — averages must not hide that equity gains may accrue unevenly across user types.

Expected exhibit: metric-vs-α curves. The honest headline has the form: *"equity re-ranking raises the priority-borough and affordable share of results by X at a Y relevance cost."* NO accuracy vocabulary anywhere ("precision", "hit rate" etc. are banned words in WS3 prose).

**Literature anchoring (for report §2; all new refs enter `references.bib` as TODO-VERIFY until a member has read them):** the evaluation stance follows the beyond-accuracy tradition (Kaminskas & Bridge 2016, ACM TiiS — diversity/novelty/coverage objectives; Herlocker et al. 2004 already in bib); the equity re-ranking sits in the **fairness-aware re-ranking / provider-side (multistakeholder) fairness** family (Burke 2017 multistakeholder recommendation; Liu & Burke 2018, personalised fairness-aware re-ranking; recent fairness-in-RS surveys, e.g. arXiv:2306.00403, arXiv:2307.04644). Our deviation from that family is principled and must be stated: with no user-interaction data, only *area/provider-side* fairness (exposure of underserved-borough provision) is estimable — consumer-side fairness is out of reach, and we say so rather than simulate it.

### 5b. Baselines, ablations, robustness (REQUIRED — cheap, high value)
The α-sweep alone compares the system with itself; exceptional evaluation situates it:
- **Baselines** (all deterministic, ~30 lines total): random-k (seeded from config), nearest-k (distance-only), and the α=1 endpoint (relevance-only). Report the full §5 metric set for each — the equity re-ranker's gains then have anchors ("vs random", "vs proximity-only"), i.e. effect sizes in context.
- **Equity-term ablation:** run with each component alone (affordable / access-info / underserved) and leave-one-out. Which component actually drives priority-borough share? One table; answers the viva question "is your equity term just a free-session filter?"
- **Robustness:** continuous `gap_index_z` vs binary `is_priority_borough` as the underserved signal — report rank correlation of the output lists and metric deltas between variants (the WS2 sensitivity ethos applied to WS3).

### 5c. Pre-registered expectations (frozen HERE, before the build — deviations are findings, not embarrassments)
- **E1:** priority-borough share@k increases monotonically as α decreases.
- **E2:** affordable share@k increases as α decreases.
- **E3:** relevance cost grows smoothly with (1−α); we characterise the curve and make **no** claim about an "acceptable" threshold — that is London Sport's policy choice, not ours.
- **E4:** catalogue coverage across the persona set at each α < 1 is at least its value at α = 1 (if not, we report and explain it).
Recording expectations before implementation is the pre-registration logic: it prevents metric-shopping after the fact and converts surprises into honest findings.

### 5d. Formal properties of the ranker (analysis for the report — prose, not code; Michael/Fahmi can draft)
Determinism buys analysability — state and prove the small propositions:
- **P1 (Pareto optimality):** the top-k list by score maximises α·Σrelevance + (1−α)·Σequity over all k-subsets (exchange argument). For **α ∈ (0,1)** — strictly positive weights — this makes every swept list Pareto-optimal w.r.t. (Σrelevance, Σequity). At the endpoints α∈{0,1} the zero-weighted objective admits dominated ties; the **lexicographic endpoint tie-break (§3.4) restores full Pareto-optimality there**. Standard caveat, stated: linear scalarisation reaches the *supported* (convex-hull) points of the frontier; non-supported Pareto-optimal lists, if any, are not visited — the sweep bounds, not exhausts, the frontier.
- **P2 (monotone traversal):** as α increases, the optimal list's Σrelevance is non-decreasing and its Σequity is non-increasing *(three-line proof: write the two optimality inequalities for α₁ < α₂ and add them)*. So the endpoints bound the attainable trade-off, and the sweep moves monotonically between them — the theoretical backbone of expectations E1/E2 (noting those concern per-list *shares*, which are related but not identical to Σequity; divergence would itself be reportable).
- **P3 (stability):** identical inputs give identical outputs; the tie-break in §3.4 is a total order. No run-to-run variance to explain away.
Half a page in the report that converts "simple method" into "analysable method" — the intellectual dividend of refusing a black box.
